# Deploy Arcie on Vercel and Supabase

Arcie uses one Vercel Services project for the web app, REST API, `/events` SSE, and the ElevenLabs custom LLM endpoint. Supabase provides Postgres. Privy verifies identity, and Circle App Kit executes confirmed actions on `Arc_Testnet`.

The Vercel project uses the repository root, Node 24.x, and pnpm 9. The root `vercel.json` builds `apps/web` with Vite and serves `apps/server/src/index.ts` with Hono on Fluid compute. The Hono build prebuilds `/assets/onramp.js`. The web service serves its own Vite assets. Set the Vercel function region to Washington, D.C. (`iad1`) and the Supabase region to US East (`us-east-1`) to keep database round trips in the same region. [Vercel Services configuration](https://vercel.com/docs/services/config-reference) · [Vercel function regions](https://vercel.com/docs/functions/configuring-functions/region)

## Provision and verify a preview

Get explicit user approval for **each numbered step** before running it. Record the exact commit, environment, target, and outcome without recording credentials, session IDs, or application records. Complete the [whole-branch review](vercel-supabase-review.md) before release.

1. **Approval required — Provision Supabase.** Choose the organization, plan, and US East region for the cutover project. Get separate approval for a rehearsal database or branch with its own credentials and empty schema. Privy login, voice sessions, and confirmations write records, so run them with rehearsal credentials and test accounts. Keep the cutover database free of application records until the import. Keep `arcie` out of the exposed Data API schemas and use server-side Privy for identity.
2. **Approval required — Provision the runtime login.** Use a separate `arcie_login` role with `LOGIN`, `INHERIT`, and membership in `arcie_runtime`. Use a restricted `NOLOGIN` grant role for `arcie_runtime`. Keep both roles free of ownership, superuser, role/database creation, replication, and RLS bypass. The migration validates the grant role, sets schema/table privileges and runtime-only RLS policies, and denies `anon` and `authenticated`. Keep the schema owner and its credential separate.
3. **Approval required — Configure Vercel.** Select Services, the repository root, Node 24.x, Fluid compute, `iad1`, and deployment protection for previews. Scope variables to the relevant environment. Set Preview `DATABASE_URL` to the rehearsal transaction pooler on port 6543, with the exact host from Supabase's **Connect** dialog and the username `arcie_login.<project-ref>`. Encode reserved characters in the password. Set `DATABASE_POOL_MAX=3` and `DATABASE_SSL=require`. Arcie verifies the certificate chain and hostname and sets `prepare: false` and `max_pipeline: 1`. Obtain the project's CA from Supabase's database SSL configuration, and inject the PEM contents into `DATABASE_SSL_CA` for the endpoint if its chain requires that trust root. A connection that fails certificate or hostname verification must stay closed. [Supabase database connections](https://supabase.com/docs/guides/database/connecting-to-postgres) · [Supabase SSL enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement)

   Set `AUTH_MODE=privy`, the Privy app credentials, server-only Circle/OpenAI/ElevenLabs settings, and the matching `LLM_SHARED_SECRET`. Use the approved rehearsal origin in Privy's allowed origins, set the Onramp environment and referrer for that origin, and keep testnet welcome drips disabled during verification. Use the dashboard's sensitive inputs or an approved secret manager that injects values without echoing them. Keep secrets out of build output, shell arguments, and browser variables. Never upload `.env` or `recovery/`. Keep `DATABASE_MIGRATION_URL` out of Vercel.
4. **Approval required — Apply schema migrations.** Approve each database target explicitly. From the repository root on Node 24, securely inject `DATABASE_MIGRATION_URL` and, when needed, `DATABASE_SSL_CA` into the migration process and run `pnpm db:migrate`. The URL uses the schema owner over a direct or session-mode connection on port 5432 with verified TLS. Arcie rejects the transaction port for migration and runs no migrations at startup. Verify the resulting schema, RLS and browser-role denials, and that the runtime can access its tables without owning them. Use the rehearsal schema for write-path verification and check cutover-target emptiness without writing rows.
5. **Approval required — Deploy a protected preview.** Deploy the reviewed commit with its Preview settings. Verify both services use the same origin, Vite assets and `/assets/onramp.js` resolve, `GET /health` returns 200, concurrent queries through the live pooler complete with verified TLS, and unauthenticated protected API and custom LLM requests are rejected by Arcie. Check application authorization within the protected preview so the Vercel gate does not mask an application failure.
6. **Approval required — Run authenticated rehearsal checks.** Use rehearsal test accounts and the rehearsal database. Verify Privy login, that authenticated `POST /voice/session` yields a session bound to that user, and that the UI sends it as `customLlmExtraBody.session_id` and ElevenLabs propagates it to `/v1/chat/completions`. Verify the session ownership rejection, authenticated SSE delivery and resume, and one approved Arc Testnet confirmation each by voice and tap. Check the displayed disclosures, receipts, and single execution. Measure from a cold Vercel invocation to the first usable LLM response through the voice path. Cold start plus first response must fit the existing 15-second cascade timeout. Use a rehearsal ElevenLabs agent or approved test configuration if needed to reach a protected preview.

## Cut over

Each step requires explicit user approval. Keep rehearsal credentials and writers isolated throughout.

1. **Approval required — Pause legacy writers and back up SQLite.** Pause every local writer, including the local server, scripts, and incoming voice traffic. Allow in-flight calls to finish and record any unresolved submissions through the approved operations channel. Use SQLite's backup API or `.backup` to take a consistent backup that incorporates committed WAL changes. Keep it private and retain it for recovery. Verify the backup and capture source table counts without exporting records.
2. **Approval required — Import and verify.** Confirm the cutover database has the reviewed schema and no application rows. Keep all cutover writers paused and the schema fixed. From the repository root with Node 24 and pnpm 9, inject the owner `DATABASE_MIGRATION_URL` and the applicable `DATABASE_SSL_CA` into the process through the approved secret channel. Run:

   ```bash
   pnpm --silent db:import-sqlite <backup.db>
   ```

   `--silent` suppresses pnpm's script banner and backup path. Successful output contains only table counts. Compare those counts to the source, check derived sessions and user relationships, and confirm the existing demo wallet ID/address mapping through an authorized check without printing records. Check that uncertain submissions retained their state and that the audit sequence continues above the preserved IDs.

   Stop if the importer reports a conflict. `TARGET_NOT_EMPTY` means the destination already contains application data. `TARGET_SCHEMA_MISMATCH` means the schema differs from the expected target. If source validation flags missing or extra columns, verify the legacy migration history and take a compatible backup. `SOURCE_PENDING_INTENT_CONFLICT` means the SQLite snapshot has multiple awaiting-confirmation intents for one session. The transaction rolls back. Resolve the legacy conflict through an approved procedure that preserves intent and audit history, then capture a new consistent backup. Keep the original backup intact.
3. **Approval required — Publish the production runtime.** Scope production secrets to the production environment and use the restricted cutover runtime login. Verify production routing and access against the imported target, and make Vercel the sole active writer with legacy writers still paused. Keep rehearsal deployments connected to their rehearsal database.
4. **Approval required — Switch the ElevenLabs URL.** Record the previous URL and change only the custom LLM URL for agent `agent_1401m6s51b0ke7zr7se63496bhrz` to the production origin plus `/v1`. Keep `custom_llm.api_key` bound to `arcie_llm_api_key`, the backup LLM disabled, and the cascade timeout at 15 seconds. Verify a voice session reaches the production origin and the session stays bound to the signed-in user.

## Roll back

Get explicit approval for each operational change. Pause hosted writes first and establish whether the hosted runtime accepted writes or submitted any on-chain actions. Before hosted writes, restore the previous ElevenLabs URL and resume the previous runtime and SQLite writer once hosted writes are disabled. After hosted writes, retain Postgres, audit records, and submission state. Reconcile accepted and uncertain Circle and Arc submissions before restoring writes or changing backends. Recovery observes outcomes and never resubmits an action. A compatible previous deployment may use the preserved Postgres state after verification. Resuming SQLite requires an approved recovery that preserves and reconciles every committed Postgres write and on-chain submission. Keep writes paused while that recovery is unresolved.
